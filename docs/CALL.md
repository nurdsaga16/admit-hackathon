# Звонок на двоих

## Архитектура

Один Node 22.15+ процесс (`server/index.mjs`, ws 8.22.0) обслуживает комнаты, WebSocket-сигналинг и собранный `web/dist/`. Flask/Redis/Celery в этом сценарии не используются. В разработке Vite проксирует `/api` и `/signal` на 127.0.0.1:3001.

- POST `/api/rooms` создаёт случайный 128-bit room id. Ссылка даёт доступ к комнате, поэтому передавать её следует только собеседнику. Авторизации аккаунтов пока нет.
- WebSocket `/signal`: join → joined с identity и ICE config → ready с назначенным инициатором → SDP/ICE. Сервер назначает имена/ID, ограничивает комнату двумя соединениями, проверяет Origin, типы/размер сообщений, частоту сигналов. Третий получает понятный отказ.
- Инициатор создаёт offer. Отвечающий привязывает свои треки к трансиверам принятого offer, затем создаёт answer. ICE-кандидаты до remote description ставятся в очередь. Видеокамера и микрофон переключаются через replaceTrack без создания второго PeerConnection.
- Надёжный ordered RTCDataChannel `captions` передаёт текст. Caption содержит id, kind (gesture/speech/text), text, final. Отправитель на приёмной стороне определяется по участнику комнаты. Окончательные сообщения защищены от дублей, получатель возвращает ACK. Без ACK после завершения отображается «Доставка не подтверждена».
- Промежуточная речь заменяет текущий subtitle и не попадает в историю. Финальная — одна запись на recognition run + result index. Повторённая человеком та же фраза с новым индексом допустима.
- Сервер не хранит переписку и не получает медиапоток. Комнаты находятся в памяти одного процесса; горизонтальное масштабирование и постоянное хранилище отсутствуют.
- Ожидание комнаты ограничено 30 минутами. Первичное соединение — 60 сек. При `disconnected` соединение сохраняется: через 5 сек инициатор пробует ICE restart, при `failed` — сразу после завершения текущего обмена SDP. На восстановление отводится 30 сек; старый таймер подключения отменяется. Ошибка/закрытие канала сообщений запускает восстановление. Закрытие WebSocket/вкладки или выход завершает комнату. WebSocket ping/pong каждые 15 сек выявляет оборванные соединения. Автоматического повторного входа в закрытую комнату нет.
- Завершение выключает tracks, PeerConnection, data channel, WebSocket, STT и распознавание жестов. История остаётся в памяти открытой вкладки. В звонке скрытие вкладки не завершает связь; обработка жестов приостанавливается и устаревшие окна сбрасываются.

## Настройки сервера

Скопируй пример **из корня**:

```powershell
Copy-Item server/.env.example server/.env
```

`server/environment.mjs` читает `server/.env` по расположению модуля: это работает и для `npm --prefix server start`, и для `node server/index.mjs` из корня. Переменные окружения процесса имеют приоритет. Без файла STUN по умолчанию — `stun:stun.l.google.com:19302`, TURN отсутствует, policy — `all`. Явное `STUN_URLS=` отключает STUN. При старте выводятся только наличие файла, числа STUN/TURN URL и policy. Фронтенду `.env` не требуется: API и WebSocket доступны через тот же origin.

| Переменная | Значение / назначение |
|---|---|
| HOST | `127.0.0.1` локально; `0.0.0.0` для сетевого интерфейса |
| PORT | `3001`; Vite dev proxy ожидает именно этот порт |
| ALLOWED_ORIGINS | Список origin через запятую, без завершающего `/`; по умолчанию локальные Vite-адреса. Собственный origin сервера допускается также |
| TLS_CERT_FILE | Путь к PEM сертификату/цепочке, доверенному обоими устройствами |
| TLS_KEY_FILE | Путь к приватному ключу сертификата; остаётся на сервере |
| STUN_URLS | Через запятую; default `stun:stun.l.google.com:19302`; пустое значение отключает STUN |
| TURN_URLS | Например `turn:relay.example:3478?transport=udp,turns:relay.example:5349?transport=tcp` |
| TURN_SHARED_SECRET | coturn REST shared secret; никогда не выдаётся клиенту |
| TURN_TTL_SECONDS | Срок временных credentials, default 3600, пределы 600–86400 сек |
| ICE_TRANSPORT_POLICY | `all` или `relay`; relay требует настроенного TURN |
| MAX_ROOMS | Максимум одновременно хранимых комнат, default 1000 |

TURN username = `expiry:participant-id`, credential = base64(HMAC-SHA1(secret, username)), по [документации coturn](https://github.com/coturn/coturn/blob/master/README.turnserver). TURN-сервер и открытые relay-порты нужны отдельно; переменные не разворачивают coturn. Временные credentials не обновляются автоматически внутри долгого звонка: после истечения TTL восстановление через TURN может потребовать новой комнаты. Google STUN видит сетевые метаданные; его можно заменить своим.

## Quick Tunnel: 101 есть, но звонок не соединяется

HTTP 101 подтверждает переход `/signal` на WebSocket, а не обмен answer, выбранную пару ICE или открытие RTCDataChannel. Quick Tunnel публикует локальный HTTP/WSS-сервис; медиатрафик SignBridge идёт через WebRTC между браузерами, напрямую либо через внешний TURN. Публичный HTTPS-адрес не становится TURN-сервером.

В проверенной рабочей папке `server/.env` отсутствовал. Ответ `joined` запущенного сервера на 127.0.0.1:3001 показал **STUN 1, TURN 0, policy all**. Присланная пользователем строка «Соединение не установлено. Для этой сети может потребоваться TURN…» соответствует прежнему 30-секундному таймеру ожидания WebRTC и канала данных. Это подтверждённое место завершения. Отсутствие TURN — вероятная причина невозможности подобрать путь между этими сетями, но без журнала с двух устройств нельзя доказать конкретный NAT/firewall или исключить недоступность STUN.

### Настроить настоящий TURN

Нужен доступный обоим устройствам внешний TURN с поддержкой **coturn REST shared-secret credentials**. Реализация генерирует временные username/password на сервере. Общий `TURN_SHARED_SECRET` должен совпадать с `static-auth-secret` вашего coturn; пароль обычного TURN-аккаунта вместо него не подходит. TURN этой задачей не разворачивается.

В `server/.env`:

- `ALLOWED_ORIGINS` — фактический HTTPS origin текущего Quick Tunnel без завершающего `/`, при необходимости через запятую с dev-origin. После смены адреса обновить настройку. Не отключать проверку Origin.
- `STUN_URLS=stun:stun.l.google.com:19302` либо свой доступный STUN.
- `TURN_URLS` — настоящие `turn:` / `turns:` URL вашего TURN через запятую. Для ограниченных сетей нужен поддерживаемый сервером TCP/TLS endpoint. Не ставить сюда HTTPS URL туннеля.
- `TURN_SHARED_SECRET` — настоящий общий REST secret coturn, только в серверном окружении. Не отправлять его в чат, не помещать в `VITE_*` или Git. Временные credentials закономерно получает браузер для доступа к TURN; журнал их не содержит.
- `TURN_TTL_SECONDS=3600` — срок выдаваемых credentials. Долгий звонок после его истечения может потребовать новую комнату для восстановления.
- `ICE_TRANSPORT_POLICY=relay` — временно для проверки именно TURN; после успешного теста вернуть `all` и перезапустить сервер. Без настроенного TURN режим relay отклоняется при старте.

Реальные адреса и секреты не подставлены. После заполнения настроек:

```powershell
npm --prefix web run build
npm --prefix server start
```

Перезапусти прежний процесс сервера, если порт уже занят. В другом терминале запускай установленный `cloudflared`: `cloudflared tunnel --url http://127.0.0.1:3001`. После появления публичного адреса внеси его origin в `.env` и перезапусти Node; туннель оставь работающим. Второму устройству передай ссылку комнаты с публичным HTTPS origin.

### Диагностика повторного сбоя

Открой «Диагностика → Диагностика соединения»; на телефоне вход через «Помощь». Журнал остаётся и на экране завершения. Скопируй его **с обоих устройств**:

- `WebSocket открыт`, роль offerer/answerer, `SDP offer/answer отправлен`, `RemoteDescription установлен` у обоих.
- Числа STUN/TURN, состояния сбора ICE, очередь/принятие/ошибки кандидатов, состояния WebRTC/ICE/канала.
- `Выбранный путь: … relay …` подтверждает выбранный relay. Одного наличия TURN URL недостаточно.
- Код STUN/TURN 701 сообщает о недоступности конкретного сервера при сборе; отдельная такая ошибка не доказывает провал всего ICE. Проверить DNS, порты, TLS и авторизацию TURN.
- `WebSocket закрыт: код …` — отдельный сбой сигналинга/туннеля. Тайм-аут подключения при открытом WebSocket требует проверки ICE/канала данных.

Журнал ограничен 120 строками в памяти вкладки. Только заданные описания, состояния, типы кандидатов, коды ошибок и тип выбранного пути: без IP, SDP, ufrag, URL серверов, текста исключений и credentials.

### Обязательная физическая проверка

Открыть общую HTTPS-ссылку на двух устройствах: Wi-Fi и мобильная сеть. В режиме `relay` подтвердить живое видео/звук в обе стороны, строку выбранного пути с relay и одну доставку сообщения с ACK. Кратко переключить сеть, проверить восстановление, затем завершить звонок. Эти проверки **не выполнены автоматически**, проблема публикации пока не считается закрытой. Локальный тест двух Chromium с синтетическими камерами проверяет только реализацию.

Источники: [W3C — addIceCandidate](https://www.w3.org/TR/webrtc/#dom-rtcpeerconnection-addicecandidate), [состояния ICE](https://www.w3.org/TR/webrtc/#dom-rtciceconnectionstate), [Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).

## Два устройства: запуск и ручная проверка

### В одной сети, с собственным доверенным сертификатом

Пример адреса компьютера — `192.168.1.20`, замени на свой. Нужен сертификат для этого IP/имени, доверенный на **обоих** устройствах. Сертификат и доверие не создавались автоматически в этой задаче.

В `server/.env`:

```dotenv
HOST=0.0.0.0
PORT=3001
TLS_CERT_FILE=C:/certs/signbridge.pem
TLS_KEY_FILE=C:/certs/signbridge-key.pem
ALLOWED_ORIGINS=https://192.168.1.20:3001
STUN_URLS=stun:stun.l.google.com:19302
```

Из корня:

```powershell
npm --prefix server ci
npm --prefix web ci
npm --prefix web run assets
npm --prefix web run build
cd server
npm start
```

Открыть `https://192.168.1.20:3001` на обоих устройствах. Firewall должен пропускать выбранный TCP-порт; настройки системы здесь не изменялись. Предупреждение о недоверенном сертификате нужно устранить установкой корректного доверия, а не обещать работу камеры после обхода предупреждения.

### Между разными сетями

Разместить тот же сервер за общедоступным HTTPS-адресом с WSS (`/signal`), проксируя также `/api` и статику. В ALLOWED_ORIGINS указать публичный HTTPS origin. Добавить доступный TURN с тем же REST secret. Общие TURN-секреты нельзя помещать в VITE_* или frontend-файлы. HTTPS deployment и реальные TURN-соединения в этой задаче не выполнялись.

### Сценарий

1. На первом устройстве ввести имя, создать комнату и разрешить камеру. На втором открыть скопированную HTTPS-ссылку, ввести другое имя и подключиться. У обоих должно появиться живое видео собеседника.
2. Включить микрофоны отдельно; проверить звук в обе стороны и выключение микрофона/камеры. Использовать наушники.
3. У первого включить жесты. Проверить реальные точки и подсказки отсутствия руки/края кадра. Если модель дала верный устойчивый черновик, подтвердить. У обоих должна появиться ровно одна запись с именем отправителя; у отправителя — «Доставлено». Удержание не должно повторять сообщение.
4. У второго включить английские субтитры, произнести фразу по-английски. Во время диктовки удалённый звук выключается. У первого должен обновляться промежуточный текст, затем появиться одна окончательная запись. Остановить STT и проверить восстановление удалённого звука.
5. Исправить неточность отдельным текстовым сообщением. Попробовать третьего участника: комната должна быть занята.
6. Завершить звонок: у обоих история, индикаторы камеры/микрофона погасли. Для повторного звонка создать новую комнату.
7. Отдельно проверить потерю сети, отказ разрешений и закрытие вкладки. Для доказательства TURN выставить `ICE_TRANSPORT_POLICY=relay`, перезапустить сервер, создать новую комнату и проверить разные сети (например Wi-Fi и мобильную). В браузерных WebRTC diagnostics выбранная candidate pair должна иметь relay. Локальный тест без TURN этого не доказывает.

## Speech-to-text

Используется `SpeechRecognition` или `webkitSpeechRecognition`, язык `en-US`, continuous + interimResults. Семантика промежуточных и финальных событий взята из [Web Speech API](https://webaudio.github.io/web-speech-api/), интеграция Chrome сверена с [официальным примером](https://developer.chrome.com/blog/voice-driven-web-apps-introduction-to-the-web-speech-api/).

В установленном Chromium 140 проверено наличие обоих конструкторов. Наличие API не доказывает доступность удалённого сервиса: network/service-not-allowed/not-allowed отображаются отдельно. Реальное распознавание аудио сервисом не проверено. Firefox/Safari/Edge и мобильные версии отдельно не тестировались; интерфейс использует feature detection, не обещает поддержку по одному названию браузера.

`start()` без audioTrack использует **локальный микрофон по умолчанию**; ни удалённый MediaStream, ни смесь звука не передаются распознавателю. Выбор отдельного устройства пока отсутствует. WebRTC-микрофон запрашивает echoCancellation/noiseSuppression/autoGainControl. Эти настройки не гарантируют обработку независимого входа SpeechRecognition; поэтому удалённый video element muted на всё время диктовки, включая ожидание запуска. Микрофон нельзя выключить, оставив STT работающим: отключение отменяет распознавание. Гарантии отсутствия акустического эха нет — требуется проверка устройств.

После штатной остановки сервису даётся до 2 секунд на финальный результат, затем abort. На end сервис не перезапускается автоматически. На разрыв/выход обработчики отключаются, запоздавшие результаты не отправляются. Сервис браузера может отправлять звук наружу; локальность заявляется только для **жестовой модели**.

## Что проверяют тесты

`npm --prefix server test` — комнаты, SDP/ICE relay, лимит 2, Origin, уход/обрыв, временные TURN credentials.

`npm --prefix web test` — признаки/scaler/stability и reducer переписки/речи. `npm --prefix web run test:browser` — Chromium с двумя контекстами, настоящим PeerConnection и DataChannel. `cd web; npx playwright test --config playwright.production.config.ts` — собранное приложение через Node на тестовом порту 3002.

Видео и аудио тестового браузера синтетические; проверяется получение RTP в обе стороны и освобождение ресурсов. SpeechRecognition подменён только внутри теста для проверки interim/final/дублей/приглушения. Gesture transport fixture также маркирован synthetic и отделён от реального численного теста ONNX/Keras. Фиктивных собеседников и транскрипций в коде приложения нет.

## Оставшиеся требования

Проверка трёх реализованных условных команд на физических камерах, проверенные данные новых выражений, реальная оценка исходных жестов, cross-network/TURN, живая речь и мобильные устройства. Постоянные требования AGENTS.md сохранены. Новые классы не объявлены обученными.
